### K-4 · Analytics top-links accepts an impossible date such as 2026-02-30 and silently shifts the window · Case file (Bahrain business-day windows) · Severity: Low

**What's wrong:** `GET /v1/analytics/top-links?from=2026-02-30&to=2026-03-05` answered `200` with the links paid from 2 March onwards, as if the merchant had asked for 2 March. The validator's own comment says it "rejects 2026-02-30", and the other three analytics endpoints answer `400 invalid_date` for the same input.

**Why it happens:** `apps/api/src/routes/analytics.ts:24-25` `isValidDateString` checks only the `YYYY-MM-DD` shape and `!Number.isNaN(Date.parse(value))`. V8's `Date.parse` rolls an out-of-range day over instead of failing (`Date.parse("2026-02-30")` is 2 March; only month 13 or day 32+ give `NaN`). Volumes, payout trends and recent ledger activity pass the string to Postgres, whose `::date` cast raises 22008, which the error handler maps to 400 (HUNT-1). Top-links instead converts the string in JavaScript (`bahrainLocalMidnightUtc`, `analytics.ts:58-60`, `new Date("2026-02-30T00:00:00+03:00")`), which rolls over the same way, so the bad date never reaches Postgres.

**What it breaks:** a merchant who asks for an impossible date gets a different window than the one requested, with a 200 and no error, so the dashboard can show a "top links" list for a period that does not exist. Four endpoints that share one validator also disagree on the same input.

**Why it needed a fix:** a report window must be the Bahrain business days the caller asked for (case file), or an error. HUNT-2 fixed the same "impossible date silently shifts the window" defect in the settlement reports. This is the analytics copy of that defect, in a different validator.

**Fix:** `apps/api/src/routes/analytics.ts:25`
```diff
-  return DATE_RE.test(value) && !Number.isNaN(Date.parse(value));
+  return DATE_RE.test(value) && !Number.isNaN(Date.parse(value)) && new Date(value).toISOString().slice(0, 10) === value; // K-4: Date.parse rolls 02-30 over to 03-02
```
Commit: this commit. Lines: prod +1/-1, test +7/-0.

**Why this is the smallest correct fix:** this is the single validator all four endpoints call, and the round-trip check is exactly the guarantee its comment already promises ("also round-trips through Date"). `new Date("YYYY-MM-DD")` is UTC midnight, so `toISOString().slice(0, 10)` returns the input unchanged for every real date and a different date for any rolled-over one. The `NaN` check runs first, so `toISOString` never sees an invalid date. *Why not validate in `bahrainLocalMidnightUtc`?* That fixes only top-links and leaves the shared validator lying about what it checks.

**Proof:** `K-4: top-links rejects an impossible calendar date (2026-02-30) with 400` (`apps/api/src/routes/analytics.test.ts`). Before the fix: `actual { status: 200 }`, `expected { status: 400, error: 'invalid_date' }`. After: passes. `analytics.test.ts` and `analytics.refunds.audit.test.ts` pass 15/15.

**Regression risk:** none for real dates. Volumes, payout trends and recent ledger activity already returned 400 for these inputs (through Postgres), so only top-links changes, from 200 to 400.
