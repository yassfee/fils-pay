### K-7 · Replaying an old settlement.paid still writes a second payout instruction (gap in the CW-1 fix) · INC-2026-08-21 · Severity: Medium

**What's wrong:** CW-1 made `settlement_payout_disbursements` hold one payout-rail instruction per paid batch, but only for rows created after its cutoff. A batch whose disbursement row was written before `2026-10-30 00:00+03` (every batch paid before the fix) got a second instruction the next time the `settlement.paid` pre-delivery effect ran for it. A merchant triggers this by replaying their own old `settlement.paid` delivery, and an admin by replay-batch or archive replay.

**Why it happens:** `apps/api/src/webhooks/payoutDisbursement.ts:15-17` inserted with `ON CONFLICT (settlement_batch_id) WHERE created_at >= '2026-10-30 00:00:00+03' DO NOTHING`. The unique index in `db/migrations/0087_settlement_payout_disbursements_unique_batch.sql:5-7` is partial on that same cutoff, so a pre-cutoff row is not in the index and cannot conflict with a new row. A replay creates a fresh delivery row with `attempt_count = 0` (`webhooks/replay.ts:43-47`), and the dispatcher runs the effect for any row at attempt 0 (`webhooks/dispatcher.ts:162-165`). The CW-1 follow-up test pinned the gap as intended (`payoutDisbursement.test.ts`: `rowCount 3, "two historic rows kept + one new row"`), although the test above it states the goal "one payout-rail instruction per paid batch, however many times the effect runs".

**What it breaks:** the audit test seeds a paid batch with its original instruction dated 2026-10-01 and runs the effect once, as a replay does. The batch then has two payout instructions for the same 10,000 fils, while the ledger has one payout leg pair. Any batch paid before the fix can be doubled this way once, and the merchant can set it off from the dashboard (`POST .../deliveries/:deliveryId/replay`, owner/finance). This is the INC-2026-08-21 class: duplicate payout instructions that disagree with the ledger by the net payout.

**Why it needed a fix:** the table exists to record one payout-rail instruction per paid batch (CW-1), and a merchant-reachable path still breaks that for all historic batches.

**Fix:** `apps/api/src/webhooks/payoutDisbursement.ts:16-17`
```diff
     `INSERT INTO settlement_payout_disbursements (settlement_batch_id, amount_fils, disbursement_reference)
-     VALUES ($1, $2, 'disb_' || gen_random_uuid())
+     SELECT $1, $2, 'disb_' || gen_random_uuid()
+      WHERE NOT EXISTS (SELECT 1 FROM settlement_payout_disbursements WHERE settlement_batch_id = $1) -- K-7: also rows before the 0087 cutoff
      ON CONFLICT (settlement_batch_id) WHERE created_at >= '2026-10-30 00:00:00+03' DO NOTHING`, // CW-1: once per batch (0087)
```
and the CW-1 follow-up assertion in `apps/api/src/webhooks/payoutDisbursement.test.ts` (3 → 2: the historic rows are kept, and no third instruction is added).
Commit: this commit. Lines: prod +2/-1, test +15/-1.

**Why this is the smallest correct fix:** the existence check sees every row, old or new, so the effect adds an instruction only for a batch that has none. The partial unique index and `ON CONFLICT` remain the guard against two concurrent first inserts, which a `NOT EXISTS` alone cannot stop. Historic duplicates are still neither deleted nor rejected, as CW-1 intended. *Why not a new migration with a full unique index?* It cannot be built while historic duplicates exist, and deleting financial records is what CW-1 deliberately avoided. *Why not skip the effect on replays in the dispatcher?* That changes delivery code CW-1/CW-12 own, and the effect would still be wrong for any other second run.

**Proof:** `K-7: a batch already disbursed before the 0087 cutoff gets no second payout instruction` (`apps/api/src/webhooks/payoutDisbursement.test.ts`). Before the fix: `expected: 1, actual: 2`. After: passes. `payoutDisbursement.test.ts`, `dispatcher.test.ts` and `archiveReplay.test.ts` pass 19/19, including CW-1's two-endpoint and idempotency tests.

**Regression risk:** low. New batches behave exactly as before (one row). The only change is that a batch which already has any disbursement row gets no new one. The corrected assertion is in a test that our team wrote for CW-1. If the lead disagrees with that reading, this commit can be dropped without touching CW-1.
