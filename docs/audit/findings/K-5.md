### K-5 · Authorize and capture answer 500 for a fractional, negative or string amountFils; a zero authorize reaches the acquirer first · ADR-0001 (integer fils) · Severity: Low

**What's wrong:** `POST /v1/transactions` (authorize, API key) and `POST /v1/transactions/:id/capture` answered `500 internal_error` when `amountFils` was `1.5`, `-5` or `"100"`. Authorize with `amountFils: 0` also answered 500, but only after it had already called the acquirer and been approved.

**Why it happens:** both handlers pass the raw JSON value to `toFils` (`apps/api/src/routes/transactions.ts:79,101` before the fix), outside any `try`. `toFils` (`packages/money/src/fils.ts:39-52`) throws a plain `RangeError` for a non-number, a non-integer or a negative value, and the error handler maps anything that is not an `AppError` to 500. `toFils(0)` is valid, so authorize continues: it claims the idempotency key, checks the merchant, calls `acquirer.authorize` (`payments/authorize.ts:94-100`), and only then hits `CHECK (amount_fils > 0)` on `transactions` (`db/migrations/0004_transactions.sql:13`). The whole transaction rolls back after the acquirer has already approved. The refund route, written later, validates the same field first (`routes/refunds.ts:17-19`: `!Number.isSafeInteger(amountFils) || amountFils <= 0` → 400).

**What it breaks:** a merchant integration that sends an amount in BD (`1.5`), a string or a sign error gets a server error with no hint that the amount is the problem. A zero authorize leaves an approval at the acquirer that has no transaction, hold or idempotency record on our side. ADR-0001 makes money integer fils, and the API should say so with a 4xx instead of crashing.

**Why it needed a fix:** plainly invalid input on the main money-in API must be a 4xx (the ERR-1 family), and no acquirer call should be made for an amount the schema can never store.

**Fix:** `apps/api/src/routes/transactions.ts:75,97`
```diff
       if (amountFils === undefined || !card) {
         throw new BadRequestError("invalid_request", "amountFils and card are required");
       }
+      if (!Number.isSafeInteger(amountFils) || amountFils <= 0) throw new BadRequestError("invalid_amount", "amountFils must be a positive integer number of fils"); // K-5
...
       const { amountFils } = request.body ?? {};
+      if (amountFils !== undefined && (!Number.isSafeInteger(amountFils) || amountFils < 0)) throw new BadRequestError("invalid_amount", "amountFils must be a non-negative integer number of fils"); // K-5
```
Commit: this commit. Lines: prod +2/-0, test +31/-0.

**Why this is the smallest correct fix:** one guard per handler, placed before anything runs, using the same predicate as the refund route and the `invalid_amount` code that payment-link creation already returns for a bad amount. Valid requests are unchanged, so the checkout and capture flows behave exactly as before. Capture keeps its current answer for `0` (`capture_exceeds_remaining` from `capture.ts:148`), because that is not a crash and its status code should not change. *Why not map `RangeError` to 400 in the error handler?* A `RangeError` can also come from a server-side money bug (UI-NEG-1 was one), and those must stay 500s. *Why not change `toFils`?* It is the shared money primitive, and its contract (throw on bad input) is correct. The routes were simply not catching its error.

**Proof:** `K-5: authorize and capture answer 400 invalid_amount for a non-positive or non-integer amountFils` (`apps/api/src/routes/transactions.audit.test.ts`). Before the fix, all seven cases were `500 internal_error`. After the fix, all seven are `400 invalid_amount`. `transactions.audit.test.ts`, `transactions.test.ts` and `payments/capture.audit.test.ts` pass 19/19, and `tsc --noEmit` is clean.

**Regression risk:** only requests that used to crash change. The idempotency key is not claimed for a rejected amount, so a corrected retry with the same key proceeds normally.
