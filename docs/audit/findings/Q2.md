### Q2 · CSV import reads a decimal-comma amount "4,75" as 4.000 BD · F7 · Severity: Medium

**Lead:** Team 45 heads-up list (Q2), verified by us.

**What's wrong:** After IMP-3, the adjustment CSV still accepts `<merchant>,4,75` (a 4.75 BD amount typed with a decimal comma, as European-locale sheets export it, and with no reason column). The row splits into amount `"4"` and reason `"75"`, and the import posts 4.000 BD: 750 fils short, with no error.

**Why it happens:** `apps/api/src/admin/adjustmentCsvParsing.ts:45` splits each row on every comma. IMP-3's guard at `:52` rejects more than three cells, or a reason that is exactly a three-digit group (the remainder of a thousands separator). A decimal comma leaves a reason of one to three digits (`4,7`, `4,75`, `4,750`), and only the three-digit case matched. `parseAdjustmentAmountFils("4")` then returns 4000 fils, and `POST /v1/admin/adjustment-imports` (`routes/adminAdjustmentImport.ts:59`) posts it.

**What it breaks:** The ledger gets 4000 fils instead of 4750 for `merchant,4,75`, and -4000 instead of -4500 for `merchant,-4,5`. The import row looks valid and the merchant balance is wrong by the fractional part.

**Why it needed a fix:** Case file F7 ("Something is wrong with how it reads BD amounts"). This is the third way the same import misreads a BD amount (after IMP-1's scaling and IMP-3's thousands separator). Money must be right to the fils.

**Fix:** `apps/api/src/admin/adjustmentCsvParsing.ts:52`
```diff
-    if (cells.length > 3 || /^\d{3}(\.\d*)?$/.test(reason ?? "")) { // IMP-3: "1,250.000" split into "1" + "250.000"
+    if (cells.length > 3 || /^\d{1,3}(\.\d*)?$/.test(reason ?? "")) { // IMP-3/Q2: "1,250.000" or decimal comma "4,75" left a digit-group reason
```
A row whose reason is one to three bare digits (the shape a split decimal comma leaves) is rejected with `invalid_csv_row`, like the other row errors, so nothing in the import is posted.

**Why this is the smallest correct fix:** one quantifier in the guard IMP-3 already placed at the single split point. *Why not accept a decimal comma and rewrite it to a dot?* The format has no quoting, so `4,75` cannot be told apart from amount `4` with reason `75`; guessing could post the wrong amount the other way. Rejecting fails closed and the operator fixes the cell. *Why not reject every numeric reason?* A reason such as `2026` cannot be a decimal-comma or thousands remainder (those are at most three digits), so it stays allowed.

**Proof:** `Q2: a decimal-comma amount is rejected, not read as its integer part` (`apps/api/src/admin/adjustmentCsvParsing.audit.test.ts`). Before the fix: `Missing expected exception.` (the row parsed as amount `"4"`, reason `"75"`). After: passes; `4.75,2026 true-up` still parses.

**Regression risk:** A reason of only one to three digits (for example `12`) is now refused; it is indistinguishable from a split amount, so this is the safe side. `adjustmentCsvParsing*.test.ts`, `adjustmentImport*.test.ts` and `routes/adminAdjustmentImport.test.ts` pass (36/36).
